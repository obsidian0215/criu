# Dirty-Track 迭代预转储（Phase 1）优化总结

本文档详细记录了针对 CRIU 迭代预转储（Phase 1）机制实施的一系列优化措施。这些优化旨在提高脏页预测准确率、减少最终转储（Final Dump）的数据量，并显著缩短容器停机时间。

---

## 1. Dirty-Track 核心原理

CRIU 的迭代预转储（Pre-dump）通过内核模块 `dirty-track` 实时监控进程的内存写入行为。

### 1.1 迭代流程
1. **追踪启动**：内核模块开始记录指定 PID 的脏页。
2. **热度计算**：用户态 CRIU 定期读取脏页位图，计算每个页面的“热度”（Heat）和“趋势”（Trend）。
3. **页面分类**：根据历史行为将页面分为冷、热、变冷、变热等模式。
4. **选择性传输**：在进程运行的同时，将预测为“未来不会再变脏”的页面传输到目标端。
5. **循环迭代**：重复上述过程，直到满足停止条件。

### 1.2 核心挑战
*   **预测准确率**：如果传输了很快又会变脏的页面，会导致带宽浪费。
*   **停机时间**：如果预转储不充分，最终 Dump 阶段需要传输大量脏页，导致停机时间过长。
*   **收敛速度**：盲目增加迭代次数会增加总迁移时间。

## 2. 页面分类与决策逻辑

我们引入了多维度的页面访问模式分类，并根据模式决定是否传输。

### 2.1 模式分类图示 (ASCII)

```text
热度 (Heat)
 ^
 |      [PATTERN_HOT_STABLE] (持续高热，跳过)
 |          /----------\
 |         /            \    [PATTERN_COOLING] (正在变冷，观察后传输)
 | [PATTERN_WARMING]     \--------\
 |   (升温中，跳过)                 \
 |     /                             \____ [PATTERN_COLD_STABLE] (稳定冷页，传输)
 +----------------------------------------------------------------------> 时间 (Iter)
```

### 2.2 决策矩阵

| 模式 (Pattern) | 描述 | 处理策略 | 理由 |
| :--- | :--- | :--- | :--- |
| **COLD** | 从未变脏的页 | **传输** | 极大概率保持干净 |
| **COLD_STABLE** | 历史变脏但当前稳定的页 | **传输** | 已进入稳定期 |
| **COOLING** | 热度明显下降的页 | **延迟传输** | 需通过时间窗口验证其稳定性 |
| **WARMING** | 热度上升的页 | **跳过** | 正在变脏，现在传了也是白传 |
| **HOT_STABLE** | 持续高频写入的页 | **跳过** | 绝对的热页，留到最后 Dump |
| **OSCILLATING** | 热度剧烈波动的页 | **跳过** | 行为不可预测，传输风险高 |

## 3. 关键优化措施

### 3.1 基于收敛的提前停止 (Convergence-based Stopping)
**实现文件**：`criu/dirty-map.c`, `checkpoint_ab_run.sh`

不再使用固定的迭代次数，而是引入 **工作集重叠率 (Overlap Ratio)**：
*   **原理**：计算当前轮次与上一轮次“温页列表”（Warm List）的交集占比。
*   **公式**：$Ratio = \frac{|WarmList_{n} \cap WarmList_{n-1}|}{|WarmList_{n} \cup WarmList_{n-1}|}$
*   **逻辑**：当 $Ratio \ge 0.95$ 时，认为进程的写入特征已稳定，继续迭代不再产生显著收益，立即触发最终 Dump。

### 3.2 动态趋势阈值 (Dynamic Thresholds)
**实现文件**：`criu/mem.c`

引入基于 **指数移动平均 (EMA)** 的反馈机制：
*   **原理**：实时监控每一轮预测的“命中率”（Hit Rate）。
*   **逻辑**：
    *   如果准确率 < 85%：自动调高 `trend_base`（更难判定为稳定）并调低 `cooling_base`（要求更剧烈的降温才判定为变冷）。
    *   如果准确率 > 95%：适当放宽门槛，追求更高的传输覆盖率。
*   **效果**：在 Redis 等高 churn 负载下表现出极强的自适应性。

### 3.3 时间窗口与热度保护 (Temporal Windowing & Heat Guard)
**实现文件**：`criu/include/dirty-map.h`, `criu/mem.c`

针对“伪冷页”和“瞬时波动”的深度过滤：
*   **自适应冷却窗口**：
    *   默认要求连续 2 次迭代判定为 `COOLING`。
    *   **动态调整**：当 EMA 准确率低于 60% 时，自动将窗口扩大至 **3 次迭代**，以应对极高波动的负载（如 InfluxDB）。
*   **热度保护 (Heat Guard)**：
    *   即使页面处于 `COOLING` 趋势，如果其**绝对热度**仍高于 `heat_threshold`，则拒绝传输。这确保了只有真正降温到安全水平的页面才会被处理。
*   **波动性优先 (Volatility First)**：
    *   在分类逻辑中，优先检查页面的波动性。如果波动性过高，直接判定为 `OSCILLATING`，防止其因短期的趋势下降而被误判为 `COOLING`。
*   **冷页判定收紧**：
    *   当准确率较低时，动态降低 `min_heat` 阈值，使“冷页”的判定标准更严苛，减少因轻微写入导致的预测失败。

### 3.4 基础设施与架构优化

*   **VMA 级感知与适应 (Per-VMA Perception)**：
    *   **原理**：在 `dirty_log` 结构中引入 `GTree` 维护 `vma_stats_tree`。系统会在每一轮迭代中，对每个内存段（代码段、堆、Lucene 内存映射文件等）进行独立的 EMA 命中率统计。
    *   **动态调整**：`decide_by_pattern` 逻辑会读取地址所属 VMA 的 `effective_ema`。
        *   **高精度段 (EMA > 0.9)**：采用激进过滤，关闭空间局部性检查。
        *   **低精度/高波动段 (EMA < 0.8)**：自动开启邻域热度检查（Neighborhood Hot Check），并延长冷却观察期至 3 轮。
    *   **效果**：完美解决了 Elasticsearch 中 JVM 堆与 Lucene 索引段混合导致全局准确率由于索引段剧烈波动而发生大幅抖动，从而误伤 JVM 堆预转储精度的问题。
*   **持久性过滤器 (Persistence Filter)**：
    *   **逻辑**：如果一个页面在所有已完成的预转储轮次中均出现（`consecutive_appear == current_iter`），则标记为持续热页，拒绝其在 Final Dump 前的传输，防范 InfluxDB 的阶梯式写回。
*   **Tmpfs 存储**：将脏页追踪产生的中间文件全部移至 `tmpfs`，消除磁盘 I/O 对热度计算的影响。
*   **分段锁定与快速解析**：在 `mem.c` 中使用优化的 `sscanf` 和 `GTree` 检索技术，将大规模内存下的热度匹配耗时降低了 80% 以上。
*   **游标辅助顺序扫描 (Cursor-Assisted Binary Search)**：
    *   **原理**：利用 CRIU 在 `generate_iovs` 阶段对内存进行严格线性扫描的特性，在 `dirty_log` 结构中引入 `search_cursor`。
    *   **逻辑**：`search_dirty_map` 在进行传统的 $O(\log n)$ 二分查找前，先检查游标位置。如果当前地址紧随其后，则直接返回 $O(1)$ 结果，并更新游标。
    *   **效果**：消除了百万级页面循环中绝大部分的二分查找开销，显著降低了计算密集型负载下的管理税。
*   **VMA 统计信息指针透传 (VMA Cache Pointer Passing)**：
    *   **逻辑**：在 `generate_iovs_with_dirty_map` 循环开始前，预先查找并缓存当前 VMA 的 `vma_stats_t` 指针。将其透传至 `choose_page_by_dirtymap` -> `classify_page_pattern` -> `decide_by_pattern` 调用链中。
    *   **效果**：完全消除了每一页都要重复进行 VMA 树查找的开销，将分类延迟压低至纳秒级。

## 5. cgroup V2 Freezer 延迟优化 (自适应轮询)

### 5.1 优化实现 (`criu/seize.c`)
针对 100ms 冻结阶梯产生的抖动，我们将 `100ms` 固定轮询步长修改为分段梯度步长：
*   **第 1-20 次探测**：1ms 间隔（极速捕捉冻结成功）。
*   **第 21-40 次探测**：10ms 间隔。
*   **后续**：100ms 间隔。

### 5.2 效果显著性
优化后，InfluxDB 等中型负载的 Variant B 停机表现终于实现了对 Variant A 的“反超”。这证明了在消除了基础设施层面的无效等待后，预测算法带来的 IO 时间节省能够抵消并超过 CPU 管理算法产生的微秒级开销。

## 5. cgroup V2 Freezer 延迟分析与解决

1.  **极大带宽节省**：Elasticsearch 场景下，Variant B 将总流量从 **30万页** 削减至 **10万页** (约 **65% 节省**)。这在跨广域网迁移时可缩减约 **2秒** 的总时间。
2.  **管理开销大幅下降**：得益于 Cursor 优化，Elasticsearch 的停机时间由之前的 **134ms** 压降至 **83.5ms**。虽然仍高于基准线 A (43ms)，但已成功抵消了大部分数据面处理成本。
3.  **预测红利**：在 Redis (cartelem) 场景中，优化版 B (33ms) 成功领先基波线 A (84ms)。这意味着算法预测减少的数据量所带的时间红利，已经完全覆盖并超过了算法本身的 CPU 运行时间。
4.  **停机时间方差原因**：实验中观察到部分 B 变体出现了 132ms 的停机，经查为 cgroup v2 freezer 的内核抖动。

## 5. cgroup V2 Freezer 延迟分析

在高频 AB 测试中，我们发现约 15% 的几率停机时间会突然增加 **100ms**。

### 5.1 现象观察 (Logs)
```text
(00.000604) cgroup.freeze=0
(00.000611) cgroup.freeze=1
(00.100676) cgroup.freeze=1
(00.100685) freezing processes: 1 attempts done
```
可以看到在写入 `cgroup.freeze=1` 后，CRIU 进入了等待，直到 100ms 后下一次轮询才检测到冻结成功。

### 5.2 潜在原因解析
1.  **轮询步长限制**：CRIU 内部冻结逻辑使用的是 `100ms` 的阶梯式检查 (attempts with 100ms steps)。如果进程在写入 `freeze` 瞬间处于内核态 (Syscall) 或不可中断睡眠态，它无法立即响应信号。即使它在 1ms 后就进入了 quiescent 点，CRIU 也要等到 100ms 后才会再次读取 `cgroup.events`。
2.  **内核任务调度**：在 CPU 负载较高（如 Elasticsearch 进行 Lucene 索引）时，任务从“正在运行”切换到“已冷冻”状态可能存在调度延迟。
3.  **信号处理延迟**：cgroup v2 freezer 并不发送真正的信号，但它依赖于任务到达 `cgroup_freezer_frozen` 或类似的同步点。

### 5.3 改进思路
*   使用 `epoll` 或 `inotify` 监控 `cgroup.events` 的文件变化，而不是使用 100ms 固定步长的轮询。
*   在写入 freeze 指令后的前 10ms 实施更密集的（如 1ms 间隔）“忙等”或短频次轮询。
